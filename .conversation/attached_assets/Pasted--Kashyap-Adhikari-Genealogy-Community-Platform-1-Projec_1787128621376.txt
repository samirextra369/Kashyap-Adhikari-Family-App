# Kashyap Adhikari Genealogy & Community Platform

## 1. Project Overview

Build a production-ready cross-platform mobile application and web-based administration portal for the **Kashyap/Kashyapa Gotra Adhikari community of Nepal**.

The platform will combine:

* Digital genealogy
* Family tree management
* Automatic relationship identification
* Cultural and religious knowledge
* Community networking
* Family events
* Invitations
* Notifications and reminders
* Birth, marriage and death records
* Mourning/Jutho calculation
* Community announcements
* Private messaging
* Historical archive

The mobile application must work on:

* Android
* iOS

A separate responsive web application must be provided for administrators.

The platform must be designed for long-term preservation of genealogy data. Genealogy records must therefore be treated as historical records and must not be silently overwritten or permanently deleted.

---

# 2. Primary Objectives

The system shall:

1. Digitally preserve the genealogy of Kashyap Gotra Adhikari families throughout Nepal.
2. Allow community members to discover their ancestors and descendants.
3. Automatically determine relationships between two people.
4. Allow community members to contribute genealogy information.
5. Require approval before community-submitted genealogy changes become official.
6. Preserve information about Kashyap Rishi, Bindabasini Devi, Adhikari history and traditional rituals.
7. Provide family-event reminders and notifications.
8. Allow families to send digital invitations.
9. Support mourning/Jutho calculation based on configurable genealogy rules.
10. Provide community announcements and social interaction.
11. Preserve privacy and require consent for sensitive information.
12. Maintain complete history and audit logs of important changes.

# 5. Important Architectural Rule

The family tree must NOT be implemented as simple nested JSON stored inside a user profile.

Genealogy must be represented using individual person records and relationships between people.

At minimum, persist direct relationships such as:

* Parent → Child
* Spouse ↔ Spouse

Relationships such as:

* Grandfather
* Uncle
* Aunt
* Cousin
* Nephew
* Niece
* Grandchild

should normally be calculated from direct relationships.

The genealogy system must support people who do not have user accounts.

A genealogy person and an application user must therefore be separate concepts.

Example:

```text
User Account
      |
optional link
      |
Person Record
```

A deceased ancestor may exist as a Person record without having any User Account.

# 16. Automatic Relationship Engine

Create a relationship engine that calculates the relationship between any two connected people.

Example:

```text
Current User
   ↓ Father
Father
   ↓ Brother
Uncle
   ↓ Daughter
Person B
```

The system should return:

```text
Relationship Path:
Father → Father's Brother → Daughter

Relationship:
Cousin
```

Where possible, display a culturally appropriate Nepali relationship term.

The relationship engine must return:

* Relationship name
* Relationship path
* Number of genealogy hops
* Maternal/paternal indication where applicable

---

# 17. Relationship Search Constraints

Prevent infinite traversal.

Define maximum traversal depth.

Recommended initial maximum:

10-15 genealogy hops.

If no known path exists:

Display:

> No verified genealogy relationship could be determined from the available family records.

Never invent a relationship.

---

# 18. Relationship Caching

Because relationship traversal may be computationally expensive:

* Cache frequently calculated relationships.
* Invalidate cache when relevant genealogy relationships change.

Do not store every possible pair permanently.

# 25. Duplicate Resolution

Genealogy Admin should be able to merge duplicate people.

Merge workflow must:

1. Select primary record.
2. Review conflicting fields.
3. Review relationships.
4. Review linked account.
5. Merge selected data.
6. Re-point relationships.
7. Preserve duplicate record as merged/tombstoned history.
8. Create audit log.

Never permanently erase genealogy history silently.

* Use background processing for expensive notifications or relationship calculations where needed.

---

# 76. Offline/Low Connectivity Consideration

Nepal may have variable network quality.

At minimum:

* Show loading states.
* Handle API failures gracefully.
* Retry safe operations.
* Cache cultural content and recently viewed data where practical.
* Never lose an unsent genealogy form without warning.

Full offline genealogy editing is not required for MVP.

* Data consistency checks if required

---

# 80. Data Integrity Rules

At minimum:

1. A person cannot be their own parent.
2. A person cannot be their own spouse.
3. Prevent obvious circular parent relationships.
4. Parent relationship must not create impossible genealogy loops.
5. Duplicate spouse relationship should not be created.
6. Approved relationship changes must be audited.
7. Merged persons cannot remain as separate active genealogy nodes.
8. Deceased status must not delete genealogy.
9. Account deletion must not automatically delete genealogy history.

---

# 81. Circular Genealogy Validation

Before approving parent-child relationship:

Check whether adding the relationship would cause a cycle.

Example invalid:

```text
A parent of B
B parent of C
C parent of A
```

Reject this relationship.

---

# 82. Age Validation

Use warnings rather than absolute rejection for historical genealogy.

Example:

If recorded parent birth date occurs after child's birth:

Display validation error.

For approximate historical dates, allow admin override with reason.

---

# 83. Admin Overrides

* Reason
* Audit log

# 125. Critical Instructions to the AI Builder

Do not make unapproved genealogy modifications.

Do not assume every genealogy person has a user account.

Do not store the entire family tree as one nested object.

Do not hard-code Jutho rules.

Do not expose private evidence documents publicly.

Do not allow every community post to trigger broadcast notification.

Do not permanently delete historical genealogy when an account is deleted.

Do not calculate relationships using names.

Relationships must use immutable Person IDs.

Do not let frontend-only restrictions determine permissions.

Always enforce permissions on the backend.

Do not silently merge people.

Do not infer a relationship when no verified path exists.

Do not treat community posts as genealogy records.

Keep social/community data separate from verified genealogy data.

The completed platform should allow a member to experience the following journey:

```text
Register
   ↓
Find or create genealogy identity
   ↓
Get verified/linked
   ↓
Open Family Tree
   ↓
Explore ancestors and descendants
   ↓
Select another person
   ↓
See automatic relationship
   ↓
Follow family members
   ↓
Receive relevant life-event notifications
   ↓
Contribute genealogy updates
   ↓
Admin verifies updates
   ↓
Participate in family/community events
   ↓
Access cultural and historical knowledge
```

The most important priority is preserving **accurate, traceable, verified genealogy data**.

Social features such as posts and chat are secondary.

When a design or engineering trade-off exists, prioritize:

1. Genealogy data integrity
2. Privacy
3. Security
4. Clear administration
5. Ease of use
6. Performance
7. Social features
